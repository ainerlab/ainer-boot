# ADR-0054：受控逃逸舱、vendored 单模块例外与公开分发基线

- 状态：Accepted
- 日期：2026-09-05
- 决策者：Ainer 项目维护者
- 取代：无
- 被取代：无
- 修订：修订 ADR-0025"消费者不复制任何 Ainer 源码"的绝对立场，引入 SPI 端口优先与
  受控单模块 vendored 例外；同时将匿名可解析公开分发与管理面交付纳入阶段退出门禁

## 背景

消费者模式（BOM + Starter + Initializer）已由 `xq-platform-next` 与
`python-learning-service` 两个真实消费者验证可独立消费、升级与回滚，但它把三笔真实成本
留给了消费者：

1. **扩展点缺口的跨仓延迟**。当业务需要框架尚未预留的钩子时，唯一路径是跨仓提需求、
   改框架、发版、升级。"禁止 fork"没有回答此时怎么办，等于把扩展需求逼成违规冲动或
   无限期等待。
2. **分发的认证摩擦**。GitHub Packages 即使仓库与包已 public，Maven 解析仍要求登录
   token。这惩罚了消费者模式相对 fork 模式唯一的手上优势（零复制起步），构成第三方
   采用的自设门槛。
3. **Fork 模式"包含感"的缺口**。yudao 式脚手架 clone 即得可跑后台（页面、菜单、布局），
   Ainer 目前是纯后端，Initializer 只生成 API/持久化纵向切片，没有管理面前端生成物。
   对计划建设管理后台的消费者，这是消费者模式下体感最冷的部分。

## 决策驱动因素

- "框架代码不 fork"的结论保持不变；要修的是扩展点缺失时的响应方式，而不是引入 fork；
- 逃生舱必须显式、可计量、有升级义务，而不是静默复制；
- SPI 端口是第一响应；vendored 单模块是最后手段；
- 同一钩子被第二个消费者需要时，按既有"公共能力晋升"规则进入 Ainer 公共契约；
- 分发摩擦与管理面缺口是消费者体验问题，必须转化为可验证门禁，而不是口头承诺。

## 备选方案

### 方案 A：维持绝对禁止复制，不提供逃生舱

门禁最干净，但真实消费者一旦被扩展点阻塞，只能在跨仓等待与违规复制之间二选一，两者都
比受控例外更差。放弃。

### 方案 B：完全开放 fork，仅要求"声明即可"

消除跨仓延迟，但等于放弃版本演化与安全补丁通道；yudao 系脚手架的长期漂移已经证明该
代价。放弃。

### 方案 C：SPI 端口优先 + 受控单模块 vendored 例外 + 显式标记与升级义务

默认答案仍是 SPI；只有当 SPI 无法覆盖且等待窗口不可接受时，允许 vendoring 恰好一个
模块，且必须显式标记、接受 CI 门禁与升级 diff 义务。采用。

## 决策

### 1. 扩展覆盖：SPI 端口为第一响应

- 模块设计必须为可预见的扩展提供 port/adapter SPI；消费者通过自有实现替换默认适配器，
  不复制框架源码；
- 业务被扩展点阻塞时的响应顺序：优先使用既有 SPI；确认无 SPI 覆盖后，向 ainer-boot
  提出端口需求并给出真实用例；等待窗口期间可走第 2 条的受控 vendored 例外；
- 同一钩子被第二个消费者需要时，按"公共能力晋升"规则评估进入 Ainer 公共契约，
  vendored 实现随之退役。

### 2. 受控 vendored 单模块例外

允许消费者在满足以下**全部**条件时，vendoring（复制并内嵌）恰好一个 Ainer 模块：

- 仓库内必须存在显式标记文件（如 `vendored/ainer-module-xxx/VENDORED.yaml`），至少声明
  源版本（Ainer 版本 + 模块 artifact 坐标）、vendoring 原因、上游 issue 链接与负责人；
- 包名与公共 API 不得重命名；vendored 模块不得被再次发布、传递给其他仓库或参与公共契约；
- 消费者 CI 门禁必须：识别 `VENDORED.yaml` 并计入例外清单；检测无标记的隐藏源码副本并
  失败关闭；BOM 升级时该模块的逐版本 diff 报告作为升级证据；
- 全框架 fork、为方便而复制多个模块、以及无标记复制仍为 0 容忍；
- `独立消费` 门禁改述为：外部消费者中的 Ainer 源码副本为 0，**显式标记的 vendored 单
  模块为唯一合法例外，且必须出现在例外清单中**。

### 3. 公开分发：消除认证摩擦

- GitHub Packages 登录解析是临时状态，不是终态分发合同；
- 目标门禁：Ainer 制品可在匿名、免 token 的公开 Maven 仓库（Maven Central 或同级渠道）
  解析；达成前，消费者文档必须把 `GITHUB_PACKAGES_TOKEN` 流程维护为可用；
- 签名、SBOM、provenance 既有供应链门禁对新渠道同等适用。

### 4. 管理面：参考管理台或生成切片

- P3"前端管理面不阻塞本阶段"的边界保持；但管理面进入 P5 退出门禁：Ainer 必须提供
  **参考管理台**（消费 OpenAPI 合同的独立前端发行物）或 Initializer 管理面纵向切片
  生成，二者至少其一作为 P5 退出门禁；
- 参考管理台不是"必须使用的官方前端"，消费者可以自建；其存在目标是提供 fork 模式
  "clone 即得后台"的等价包含感，而不复制框架代码。

## 后果

### 正面

- 扩展点缺口从"违规冲动/长期等待"变为显式计量的技术债，跨仓延迟有受控出口；
- 升级 diff 报告把 vendored 模块的漂移变成可审计证据，而非无声分叉；
- 匿名可解析消除第三方采用的最高频摩擦；
- 管理面缺口有明确退出门禁与交付形态，不再无限期悬置。

### 负面与风险

- vendored 模块的安全补丁责任转移到消费者，升级 diff 报告是新增持续成本；
- 消费者 CI 需要新增"隐藏副本检测"门禁，存在误报/漏报风险；
- Maven Central 发布引入新的供应链通道（签名、验证、发布失败处置），需要新的发布演练。

## 安全、数据与隐私

- vendored 例外不改变任何运行时安全语义：授权、审计、数据隔离仍由模块在原包名下执行；
- `VENDORED.yaml` 属于供应链证据，纳入发布与审计范围；无标记复制按门禁失败关闭处理；
- 公开分发不改变制品内容与签名要求；token 只用于认证，不进入构建产物。

## 运维与迁移

- 本 ADR 生效不需要代码变更；门禁修订即时进入设计文档 §12 与消费合同 §13；
- SPI 端口补齐、vendored 检测 CI、Central 发布通道按消费者真实需求排期，不提前实现；
- 既有两个消费者当前均为 0 源码副本，无需迁移；任一消费者未来触发 vendoring，按第 2 条
  登记并接受对应门禁。

## 验收记录

- 本 ADR 为文档决策，验收以设计文档 §12/§13 门禁修订为准；
- SPI 端口机制、vendored 检测 CI、Central 匿名解析三项工程验收**未完成**，按消费者
  需求出现后排期（见 [`../../project-status.md`](../../project-status.md) §5）。
