# Ainer Boot 产品白皮书

> 面向：企业采购、平台架构师、技术决策者 · 对应版本：`v1.2.0`（当前合格稳定）
> 状态：对外草案 v0.1 —— 源码许可已定为 MIT（ADR-0051）；定价与分层仍为占位

---

## 1. 一句话定位

**Ainer Boot**（AI-Native Extensible Runtime）是一个 AI 原生、但不局限于 AI 的通用企业
Java 脚手架与运行基线：JDK 25 + Spring Boot 4.1 + PostgreSQL 18 的模块化单体，自带可信的
身份、授权、工作区治理、AI 模型网关与企业基座——让产品团队从「第一个业务提交」开始，
而不是从「搭后台」开始。

它不是一个「能跑的 demo 后台」。它是一套**带证据链的工程合同**：每一项 Stable 能力都有
自动化验证、真实数据库门禁与签名供应链背书。

## 2. 企业自建后台的真实成本

多数团队低估的不是搭建成本，而是「演示级起点」在真实业务面前的重构成本：

| 常见起点的隐性代价 | Ainer Boot 的回答 |
|---|---|
| 登录/权限是演示级的，承载真实身份前要推倒重写 | 独立 OAuth 2.1/OIDC 授权服务器、Passkey、真 JWT 端到端安全链 |
| `用户-部门-角色-数据范围` 表达不了真实组织与多任职 | 工作区成员治理 + 混合授权（RBAC+ReBAC+ABAC）+ 组织目录岗位集合绑定（撤岗即失权） |
| 错误码、响应信封、分页各自为政，联调靠口口相传 | 统一响应信封、真实 HTTP 状态码、稳定错误码族、全响应请求追踪标识 |
| 测试用内存数据库自欺，上线才暴露方言差异 | PostgreSQL 18 唯一基线；集成测试全量真实库重放，CI 强制零跳过 |
| AI 能力是「再加一个 SDK」，费用与数据边界失控 | 治理式模型网关：模型白名单、限流、预算、Token 费用审计、敏感信息脱敏 |
| 升级靠玄学，回滚没演练过 | 版本化制品 + 签名供应链 + 相邻版本升级/一级回滚窗口 + 双参考消费者真实矩阵 |

## 3. 六大能力域

### A. 现代运行基座
JDK 25 与虚拟线程、Spring Boot 4.1、PostgreSQL 18 唯一数据基线；模块化单体默认交付，
满足明确条件后按需服务化（配置只切换适配器，不改变事务边界）。Docker Compose 开发环境。

### B. 安全身份底座
独立 OAuth 2.1/OIDC 授权服务器（PKCE、Client Credentials、在线校验与撤销）；人员/服务
双轨令牌档案与在线撤销纪元比对；高风险路径选择性在线校验失败关闭；step-up 强认证策略。
Passkey 为协议能力交付（默认关闭）。

### C. 工作区与治理
工作区资源边界（所有者/管理员/成员）、所有者专用锁定事务转移、双人恢复流程；授权审计
热表 + 同库归档 + SIEM 稳定游标拉取。

### D. 通用授权
Permission/Role/Binding 混合授权引擎、结构化 Scope、管理 API、防提权矩阵、决策审计；
组织目录（部门/任职/岗位）驱动集合绑定，人事事实变化下一次决策即时生效；Agent 代行
一层委托与实时委托检查点。首版边界如实标注：端点注解为粗粒度门禁，高价值写仍需应用层
显式授权。

### E. AI 运行时
OpenAI 兼容模型网关（非流式/SSE）、模型白名单、限流、日预算、Token 费用与策略审计；
供应商错误正文与密钥不进客户端或日志。Agent 定义注册表（退役即失权）。

### F. 企业基座与知识
文件存储（SHA-256 校验、限制与补偿）、树形字典、类型安全配置（AES-GCM 加密项）、多渠道
通知（模板 + 可靠队列；生产渠道经 SPI 由产品接入）、缓存抽象与分布式锁；知识基础库
（不可变版本 + 血缘 + **人工发布门禁**——AI 只能提案）。

### G. 开发者工具链
Project Initializer：声明式清单确定性生成独立项目（自带锁定版构建 Wrapper 与真实测试），
两个参考消费者均由其生成；真 JWT 测试夹具库；发布供应链（GPG 签名、SBOM、provenance、
不可变 Release 全量读回验签）。

## 4. 为什么可以信任：三重证据模型

采购脚手架本质是采购「可验证的承诺」。Ainer Boot 的每个承诺对应一种可复核的证据：

| 承诺 | 证据形态 |
|---|---|
| 功能真实可用 | 真实 PostgreSQL 集成测试，CI 与发布流水线强制零跳过；HTTP 层测试使用真实签名 JWT 验签 |
| 升级不破坏兼容 | 两个独立业务域参考消费者在每次次版本执行全量测试 + 升级/回滚矩阵（已留档的完整升级链：rc → 0.1 → 0.2 → 1.0） |
| 制品来源可信 | 注释标签与源码三方一致才可发布；全部制品逐个签名读回验签；发布物不可变 |

兼容承诺覆盖：HTTP API 路径与响应结构、错误码语义、SPI 签名、数据库迁移只向前追加、
消费者配置元数据契约。**承诺不是声明，是每次发布都要重新通过的门禁。**

## 5. 版本与支持

- 当前合格稳定：`v1.2.0`；`v1.1.0` withdrawn；升级起点 `v1.0.0`；`1.0.x` 为首个 LTS
  工程补丁线
- 官方支持相邻次版本升级 + 一级回滚；每个次版本的发布证据必须包含至少一个真实消费者
  全量通过
- 任务调度、授权粗门禁、观测 Starter 与通知 EMAIL/WEBHOOK 已随 `1.2.0` 发布

## 6. 交付形态

| 形态 | 内容 | 适合 |
|---|---|---|
| 制品消费 | BOM + Starter + 模块制品，固定版本从受控仓库拉取 | 已有项目渐进接入 |
| Initializer 生成 | 从声明式清单生成独立项目（含构建、测试、迁移基线） | 新产品起步 |
| 参考装配 | 完整模块化单体参考应用（全部能力域装配示例） | 评估与架构参照 |

不含：前端管理界面（独立产品线）、消息中间件集成、多数据源/分库分表、托管服务。生产
高可用与容量规划属于各产品自己的部署责任——本产品交付可验证的工程基线，不是 SaaS。
